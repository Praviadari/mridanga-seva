One sentence summary. The student's own phone checks that the person in front of it is alive and is the same person whose "face code" it stored at the desk, reads its location once, gets a "this phone and app are genuine" pass from Google, and asks our server to record the check-in; the server checks everything again before it saves.

1. What face scan is (and what it is not)

Today a student checks in at the class door by showing the QR code in the app (or a printed QR card) to a coordinator. Face scan adds a second, optional way: the student taps Check in on their own phone, looks at the camera, and is checked in, but only at the class, only during class hours, and only if the face is theirs.

It is
  • Optional and separate: its own written consent. QR stays for everyone, for good.
  • 1:1 ("is this the owner of this login?"), never 1:N ("who is this among everyone?").
  • On-device: the face is turned into numbers on the phone; no photo leaves it.
  • Set up once at the desk, with a coordinator confirming it is the right person.
It is not
  • A camera at the door, a tablet, or a scan of the whole room.
  • Location tracking: location is read once, at the tap, and only "inside / outside + distance" is kept.
  • A photo store: no picture is ever saved, on the phone or the server.
  • Switched on for the class yet: it runs only in the separate TEST app, on the TEST server.

Why so careful?

A face is biometric data: you cannot change it like a password. India's Digital Personal Data Protection Act 2023 (DPDP) and its Rules 2025 ask for clear consent, keeping only what is needed, deleting it when done, and extra care for children. Our design follows that strictly: adults first, a separate consent form, the face code only on the student's phone, and everything deleted at the end of a test.

Who decided what (the decisions log)

Every rule has a numbered entry in docs/DECISIONS.md. The important ones for face scan: #212 no location tracking · #213 face is a separate opt-in, QR stays · #248 self-scan on the student's own phone only · #295 "Gate 2": no face code on the server · #296 "Gate 1": the Google integrity check · #344–#349 self-scan rules · #430–#437 the TEST app and this week's fixes.

2. Four ideas you need first

Idea 1: face detection (where is a face?)

Detection finds faces in a camera frame and gives their box and a few landmarks (eyes, nose, mouth corners), the head angles (turned left/right = yaw), and how open each eye is (0 to 1). It does not know who the person is. We use Google's ML Kit face detector, which runs on the phone.

Idea 2: an embedding (a "face code")

A recognition model (SFace) looks at a cropped, straightened face (112 x 112 pixels) and outputs a list of 128 numbers. Pictures of the same person give similar lists; different people give different lists. That list is the face code. You cannot turn it back into a photo. At the desk we take 5 pictures and store the average of their codes.

Idea 3: cosine similarity (how alike are two codes?)

Think of each code as an arrow in 128-dimensional space. Cosine similarity measures the angle between two arrows: 1.0 = same direction (same face), 0 = unrelated. In code: cosine(a, b) in src/face/face-math.ts.

Our first real test: Arjun scored 0.833 against his own code. In the October spike, the same person scored about 0.81 and different people 0.11–0.31.

Thresholds: two kinds of mistakes

MistakeWhat happensHow badOur choice
False acceptSomeone else is checked in as youSerious: wrong attendanceThreshold 0.55 (strict, setting face_match_percent = 55). A refusal only means "use your QR or ask a coordinator".
False rejectYou are refused, even though it is youAnnoying, harmless

Idea 4: liveness (is it a live person, not a photo?)

Two layers. Active: the app asks the person to blink and turn their head, in a random order (src/face/liveness.ts). A printed photo cannot do either. Passive: two small models (MiniFASNet) look at each picture for signs of paper or a screen and give a "real face" score; every picture must reach 0.8.

3. The big picture: phone, server, Google

The two "gates" (security rules from the October audit)

Gate 2: no face code on the server (#295). The server only keeps an enrolment record: who, which phone (a random device key), which model, who confirmed it, when, until when. If the server were ever leaked, there is nothing face-like to steal. A new phone = set up again at the desk.
Gate 1: the phone must prove it is genuine (#296). Before every self-scan the server hands out a one-time challenge; Google's Play Integrity signs a verdict about the phone and app; our Edge Function checks it and gives a one-time pass valid 120 seconds. A rooted phone, an emulator or a modified app gets no pass.

Why check things twice (phone and server)? The phone does the face work because the face must not leave it; but a phone can be tampered with, so the server never trusts the phone's word alone: it re-checks the integrity pass, the consent, the enrolment of this phone, the location result, the class hours, the liveness flag and the score.

4. Flow A: setting up a face at the desk (enrolment)

Happens once per student (adults: valid 24 months; children later: 12 months). Two people and two phones: the student and a coordinator.

1
Consent. The coordinator opens the student's profile → Face scan at the desk and records the signed form (record_face_consent). Nobody can record their own; under the minimum age (18 now) it refuses.
2
Allowed? The student's phone (My profile → Face scan) asks the server (my_face_enrolment). No consent or switch off → the camera never opens.
3
Scan. Blink and turn in random order; then 5 pictures 350 ms apart. Each picture: ML Kit finds the face again, it is cut and straightened, SFace gives 128 numbers, MiniFASNet gives a real-face score. Checks: at least 3 good pictures, every score ≥ 0.8, and every picture close to their average (≥ 0.5, "all one face"). The average is the face code.
4
Ask. The phone sends only its random device key and the model name (start_face_enrolment); the server answers a 6-digit code (10 minutes). The phone shows it.
5
Confirm. A coordinator, on their own phone, types the code (approve_face_enrolment). This is the "supervised" part: a person checks it is the right student. 5 wrong codes end the request; you can never confirm your own.
6
Finish. The student's phone notices (it asks every 4 s), calls enrol_face, and keeps the face code in Android's Keystore-encrypted storage (expo-secure-store). The server records "enrolled until …".

Screens: app/src/app/student/face-scan.tsx (student), app/src/app/staff/face/[id].tsx (desk). Logic: src/face/enrolment.ts, src/face/face-scanner.tsx, src/data/face.ts.

5. Flow B: checking in and out by face (self-scan)

The home screen shows a Check in circle only when: face scan is switched on, this phone holds a confirmed face code, and the class centre is open now (self_scan_state). After a check-in it shows Check out.

Check-out is never blocked by place. If the phone is outside the area at check-out, the check-out is saved and marked "away" for the staff (visits.check_out_location). A parent of a child gets the usual check-out email (from the existing parent-notice feature).

"int8" = the model's weights are stored as small integers (smaller, faster on cheap phones). The model name is also a server setting (face_model_version): changing the model ends every enrolment, and everyone sets up again.

The picture pipeline (src/face/pipeline.ts)

  1. The camera hands a frame (VisionCamera) → ML Kit finds the face on the camera thread.
  2. When a picture is wanted, the frame becomes an image (Nitro Image), saved to a temporary JPEG, ML Kit runs again on it for exact landmarks, the file is deleted in the same call.
  3. The face is rotated and scaled so the eyes, nose and mouth sit where SFace expects (alignedFaceTensor in face-math.ts); two looser crops go to the two MiniFASNets.
  4. TensorFlow Lite runs the three models; out come the 128 numbers and the real-face score.

Rules we follow

  • Consent first, separate form, nothing pre-ticked; saying no changes nothing (QR stays). The person can stop any time (Turn face scan off): the code is wiped and the server record ends.
  • Location once (#212): only at the tap; never in the background, never a map, never in a parent email.
  • Children only later: written, verifiable parent consent (DPDP Rules, rule 10), the child's own yes, minimum age decided by the Guru, and only in the real class app after the full release (docs/phase3/ADULT_TEST.md §3).
  • Data outside India: our server is in Australia (LIVE) and Singapore (TEST); the DPDP Act allows this unless a country is restricted, and the privacy notice says so.
  • Test data is deleted within 7 days of the last test session: phones (turn off, uninstall) and one SQL run on TEST with a check query (docs/OPERATIONS.md "Face scan: deleting the test face data").
For maintainers: never add a column that stores a face code on the server, never send pictures anywhere, never read location in the background, never log faces or scores with names. The smoke tests check several of these (e.g. "no column named template or embedding").

10. The TEST app, builds and updates

Why a separate app

Testers keep the real "Mridanga Seva" app (their real data) and install "Mridanga Seva TEST" next to it: a different package name org.mridangaseva.app.test, a red TEST band on the icon, the TEST server only. One line in app.config.js does it: when APP_VARIANT=facetest, the name, package, link scheme and icons change; when it is not set, the app config is byte-for-byte the real app's (we proved this, #432). A "build guard" script refuses any TEST-app build pointed at LIVE.

Fingerprint, builds and updates (the most important idea for releases)

Build (APK) = the whole app including native code. Made on Expo's servers (EAS Build), about 25 minutes, 15 free per month. Needed when native code or config changes (a new library, app.json, eas.json).
Update (OTA) = only our JavaScript, downloaded by the installed app at start. Minutes, unlimited. It reaches only APKs with the same fingerprint.

The fingerprint is a hash Expo computes from everything native (packages, app.json, eas.json, plugins). Same fingerprint = an update fits. The class's phones run fingerprint 23dc7e4a; the face branch has native face libraries, so its fingerprint differs. That is why face scan stays on its own branch until a new production APK is planned: merging earlier would stop updates reaching the class's phones.

11. Lessons from the first tests (three real bugs)

All three were invisible in development and in automatic checks, and appeared only on a real phone. Each fix also added a check so it cannot come back.

Bug 1: the app closed the moment it opened (#435)

Cause. To save space, an earlier change removed a GPU library (libtensorflowlite_gpu_jni.so) from the APK. But the TFLite library is linked to it and Android loads it at app start: a missing linked library = instant crash. The automatic check only compiled the APK, it never opened it.

Fix. Keep the library. New check: CI reads every native library in the APK (readelf) and fails if one needs a library that is missing. Lesson: "it builds" is not "it runs".

Bug 2: stuck at "picture 0 of 5" (#436)

Cause. In an installed app, bundled files are Android resources with plain names like assets_models_sface_2021dec_int8; the model loader expected a web-style address and failed with "MalformedURLException: no protocol". In development the files came from the dev server as http:// addresses, so it always worked there. Worse, the screen swallowed the error and kept waiting.

Fix. Copy each model to the app's cache with expo-asset and load the file:// copy. The scanner now stops after 3 failed pictures and says so. We found the real error with the hidden developer screen, which prints it. Lessons: test the release build, and never hide an error without telling the user.

Bug 3: uploads cut off at 9 MB

Cause. The PC had the office cable and the phone's USB tethering both on; Windows preferred the office network, whose firewall breaks large uploads to Google's storage. Fix: unplug the office cable during builds and updates. Lesson: when something fails half-way, check the network path, not only the code.

And what worked first time: the 1:1 match (score 0.833), the blink/turn challenge, Google Play Integrity through our own Edge Function, the server's re-checks, the 10-minute rule, the "outside the area" refusal, and the "two faces in view" refusal.

12. How to work on it safely

  1. Never LIVE. Work only with the TEST server (fhuqyk…) and the TEST app. The main folder's app/.env is LIVE: use a worktree with TEST values (app/.env.test copied as .env.development).
  2. Branch face-scan, never main, until the release lead merges it before a production APK.
  3. Before every commit, from app/: npx tsc --noEmit (0 errors), npx expo lint (clean), npm test (all pass); from supabase/tests/: npm test (smoke + replay).
  4. Native or JS? Check the fingerprint (npx expo-updates runtimeversion:resolve --platform android, with APP_VARIANT=facetest for the test app). Unchanged → an update is enough.
  5. Write it down: a numbered entry in docs/DECISIONS.md for every rule you add or change, and the docs it touches.
  6. Test on a phone with the developer screen (TEST builds: staff My profile → Face scan test (developer)): it shows model load times, live face numbers, and the real error of any picture.
