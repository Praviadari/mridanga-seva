# International use (i18n / l10n)

The app was built for one centre in Hyderabad (Abids), in English, Telugu and Hindi. The seva is
expanding to other countries and time zones, and to languages not yet named. This page is the
audit of every India-only or single-language assumption (7 Oct 2026, branch `i18n-audit`), what
was fixed (migration 0033, [DECISIONS.md #132-#137](DECISIONS.md)), and what waits for a team
decision. Interface text and translation rules are in [TRANSLATIONS.md](TRANSLATIONS.md).

## The rules now

- **Storage is ISO.** Moments are `timestamptz` (UTC inside); days are `date` / `'YYYY-MM-DD'`;
  money is whole minor units with an ISO 4217 code (`fund_entries.currency`); countries are
  ISO 3166-1 alpha-2 (`centres.country_code`); time zones are IANA names (`centres.time_zone`);
  languages are ISO 639-1 codes (`profiles.language`).
- **"Today" is the centre's.** Every rule about a day (attendance day, "this week" from Monday,
  days since the last visit, due dates, reminders "tomorrow", closing time) uses the time zone of
  the centre concerned: the visit's, the student's home centre, the event's or shift's, or the
  signed-in person's (`today_ist()`, which keeps its old name). pg_cron and the dashboard use the
  first centre's. In the app, `lib/dates.ts` does the same with the zone from `lib/class-locale.ts`.
- **Display follows the country, words follow the language.** `formatDate`, `formatDateTime`,
  `formatMoney` (`lib/money.ts`) and `intlLocale()` (`<language>-<country>`, e.g. `te-IN`). India
  keeps DD-MM-YYYY, 24-hour time and ₹ with lakh grouping in every language, as before.
- **Typed input stays simple.** Dates are typed day-month-year in every country (ISO 2026-10-04 is
  also read); times 24-hour. Form fields are filled with `formatTypedDate`.
- **Counts use plural keys** (`key_one`, `key_other`; i18next picks the form from `count`).
- **Search ignores Latin accents** (`lib/search-text.ts`), so "krsna" finds "Kṛṣṇa".

Opening a centre abroad today: one row in the SQL editor (G9 has no field for zone or country yet):

```sql
insert into centres (name, time_zone, country_code) values ('Queens', 'America/New_York', 'US');
```

## Proposals for the team

Each needs Praveen and the team before a centre abroad registers students.

**P1. Age of a minor per country.** India's DPDP Act treats under 18 as a child (verifiable
parental consent). The GDPR lets each EU country set 13-16 for online services (Art. 8); the UK
13; the US COPPA 13. The class also meets children in person, so the safeguarding age may differ
from the data-law age. *Recommendation:* a column `centres.adult_age smallint default 18`, read by
`is_minor` through the student's home centre and by the app (`isMinorOn`); keep 18 unless a
lawyer of that country advises lower; consent texts per country. A migration plus the consent
screens; no APK.

**P2. Phone numbers in E.164.** Today 10-13 digits, "+91" assumed in hints and the import's
duplicate check. *Recommendation:* store E.164 (`+919876543210`), with the centre's country as the
default calling code; check with `libphonenumber-js` (pure JavaScript, about 150 kB with the "min"
metadata; no native code, so OTA-safe) — **needs the lead's OK for a new dependency**. Existing
numbers: a one-off migration adding +91 to 10-digit Indian numbers. Hints in each language show
the centre's example.

**P3. Addresses.** `pincode` must be 6 digits (a table check) and `area` is free text; ID types are
Indian. *Recommendation:* rename nothing; add `students.country_code` (default the home centre's)
and check `pincode` only when the country is IN (drop the table check for a trigger that knows the
country); call it "postal code" in the interface outside India. ID types: show the list for the
centre's country (keep `passport` and `other` everywhere).

**P4. New languages.** Adding one today means: the `profiles.language` check (migration), the
`Language` type and `LANGUAGES` list (`app/src/i18n/index.ts`), one JSON file, and five SQL notice
functions (L4). *Recommendation:* name the languages first (the team said "more", not which).
Then (a) move the SQL notice wording to the app: queue a key and values, and let the app or the
Edge Function word them with the same JSON files — one place for every language; (b) allow any
ISO 639-1 code in `profiles.language` that the app ships; (c) budget a native-speaker review per
language, as for te/hi. Right-to-left languages (Urdu, Arabic) are a separate, larger piece (L9).

**P5. A fund abroad.** *Recommendation:* one fund per currency (the simplest honest ledger):
`record_fund_entry` takes the currency of the keeper's centre; the balance, limits
(`fund_approval_rupees` → per currency) and reports are per currency; the financial year start
becomes a setting (India 1 April; UK 6 April; US 1 January). Until then, centres abroad do not use
the fund.

**P6. Typed dates and times → pickers.** Typed day-month-year with hints works, but a date picker
removes every order question and gives 12-hour time where people expect it. *Recommendation:*
`@react-native-community/datetimepicker` in the next APK (brief 9, production APK), with the
typed field kept on the web.

**P7. Centre picker and zone on G9.** Students get centre 1 as home centre, and a centre's zone and
country are set in SQL. *Recommendation:* when the second centre opens: a home-centre choice on
registration (C2) and the import, and a zone + country field on G9 (a list of IANA zones for that
country from `Intl.supportedValuesOf('timeZone')` on the web, or a short typed list).

**P8. Daily jobs at each centre's local hour.** Reminders (assessments 09:00, events 09:00, duty
18:00, status refresh 06:00) run at India's hour, so abroad they arrive at night. *Recommendation:*
run each job hourly and let it act only for centres where it is now that local hour (one more
`where` on the centre's zone), with the "reminded once" columns already in place. Only needed when
the first centre outside India's day opens.
