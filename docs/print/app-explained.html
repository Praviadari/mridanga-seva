One sentence summary. One TypeScript code base (Expo / React Native) gives an Android app and a web version; both talk to one Supabase project, where a PostgreSQL database holds every record and every rule about who may see or change it, so no screen, old app or typed web address can get around the rules.
How to read this. Screen names are written as the app shows them in English, with where to find them, e.g. Welcome desk (Students tab). The docs and code comments also use short screen codes (C2, G10…) from the screen list the team approved on 28-09-2026; section 18 maps the names to the code files. A NEXT tag marks something that is on main and on TEST but not yet in the class's (LIVE) app on 24-10-2026; OFF marks a feature that is built but switched off until the Guru switches it on.

1. What the app does, and who uses it

Mridanga Seva is the app of an ISKCON mridanga (khol) class in Hyderabad. The class is drop-in: students come any time between the afternoon and evening, not in fixed batches. So the app thinks in visits (a check-in and a check-out), not in roll calls. It replaces an Excel sheet and about ten WhatsApp groups, and it keeps a proper record of consent for students under 18.

Where it runs

Android app (an APK installed from a link, not from the Play Store). Used by most staff and Android students. Gets push notifications. Updates itself over the internet.
Web version (mridanga-seva.pages.dev). Same code, in a browser. iPhone users add it to their home screen, because an App Store listing costs US$99 a year. Works partly offline. No push notifications yet.

There is also a separate public website, mridangaseva.com (folder website/): plain HTML in English, Telugu and Hindi, with the classes, how to join, the app links and the privacy notice. It shares no code with the app.

3. Five ideas you need first

Idea 1: the app keeps almost nothing of its own

The phone or browser draws screens and sends requests over the internet. The records live on the server, in the database. So every coordinator sees the same students on any phone. (A few things are kept on the device on purpose: the signed-in person's own profile so the app opens at once, My QR card so it works without signal, the practice taals, and check-ins or practice saved while offline until they can be sent.)

Idea 2: tables and rows

A database is a set of very strict registers. Each kind of record is a table (like a sheet in Excel): students, visits, call_logs… Each record is a row. A row in visits is one check-in, with its check-out time filled in later. Tables point at each other by id: a visit holds the student_id of its student.

Idea 3: the rules live in the database (the most important idea)

A screen can hide a button, but a screen is not a lock: someone could use an old app version or type a web address. So every rule that protects people or records is enforced by the database itself (DECISIONS #5). Three tools do it:

ToolWhat it isExample from our app
Row-level security (policies)Written rules per table: who may read, insert, update, delete which rowsA student asking for "all students" gets only their own row
Triggers and constraints ("guards")Checks that run whenever a row is saved; they refuse a bad saveA roll number can never change; Paused and Left only through a logged call
Database functionsActions that change several things at once, all or nothing, checking who callsscan_qr checks a student in, makes them Active and closes their call tasks

Idea 4: migrations

The database is not built by clicking. It is built by migrations: numbered SQL files in supabase/migrations/, run in number order (0001, 0002 … 0061). A migration that has run is never edited; a change is a new file. Running the same files on an empty database rebuilds the whole schema, which is how the tests work.

Idea 5: TEST and LIVE

There are two separate Supabase projects with the same schema:

Never LIVE. Real records are never used for testing and made-up students never go into LIVE (on 29-09-2026 test students were found in LIVE by mistake and removed the same day). Scripts check that a test build talks only to TEST and a live build only to LIVE (section 20).

4. The big picture

#What travels
1The app's reads and writes, over HTTPS, with the public key and the person's login token. The database checks each one against row-level security and the function's own role check.
2Supabase Auth sends sign-up confirmation and password-reset emails through Brevo (SMTP).
3Every minute a pg_cron job calls the Edge Function notify-announcements when something waits to be pushed; it hands the messages to Expo's push service.
4Expo passes them to Google Firebase, which delivers them to the Android phones. The web version gets none (yet).
5Parent emails (consent code, check-out notice, weekly summary) go from notify-parents to Brevo's API.
6Brevo delivers the emails to the parent's (or the new user's) inbox.

Read it like this: phones and browsers talk to Supabase directly. Supabase checks who you are (Auth), keeps the records and the rules (database) and the files (Storage), and runs jobs on a timetable (pg_cron). Those jobs call two small programs (Edge Functions) that hand notifications to Expo and emails to Brevo. Videos stay on YouTube. In the bottom lane, a maintainer's PC sends code to GitHub, app builds and updates through Expo EAS, and the web version to Cloudflare.

5. Journey: signing up and being accepted

Most students create their own login at home. The desk then accepts them with one tap, using what they typed, so the form is filled once, by the student (DECISIONS #263).

1
Sign up (app/src/app/sign-up.tsx). Name as on a government ID, email, password, date of birth, gender, mobile, centre (country → city → centre) and a required tick "I have read the privacy notice". The lists come from sign_up_choices(), the only function someone not signed in may run. Under 18 → the extra parent part (section 6).
2
Confirm the email. Supabase sends a link; the trigger handle_new_user already made a profiles row with role pending. Logins are linked only after the email is confirmed; otherwise anyone could claim a record by typing its email (DECISIONS #13).
3
Waiting for access (pending.tsx). About you opens once (emergency contact, how they found the class…, table person_details). An adult (or a child whose parent consented) may already use While you wait (app/src/app/waiting/, function practice_while_waiting(), 0057).
4
Welcome desk (Students tab) (staff/register.tsx). The coordinator sees the confirmed sign-ups of their centre (waiting_sign_ups()) and possible duplicates (possible_duplicates), and taps Accept. For someone without a phone or login there is still the full form (register_student).
5
Student. accept_sign_up(profile) writes the students row; a trigger gives the roll number MS-<year>-<4 digits>, frozen for ever and never reused; About you moves to the record; a mentor of the same gender is assigned; the login becomes student, and the person's app opens the student screens.
Why a separate "pending" role? Until the desk has seen the person, a login can read and edit only its own profile. The test net in supabase/tests checks, table by table, that a pending login reads nothing else.

Other paths to the same link: a coordinator saving an email on an existing record links a waiting login with that email (trigger students_link_login); the Guru links by hand (link_student_login). A minor's record is never linked automatically (0047): only by the parent-consent path or the Guru.

6. Journey: a child signs up, the parent consents

Most students are under 18. India's DPDP Rules (rule 10) ask for verifiable consent of a parent before a child's data is processed. Since migration 0051 a child can start at home, and the parent consents by email (DECISIONS #399). Before that, "under 18" meant "come to the desk with a parent", and on 20-10-2026 several children tried at home and gave up.

1
The sign-up form sees a date of birth under 18 and asks the parent's name, relation (mother, father, guardian), email and mobile. The database keeps them in minor_signups, a table no app user can read.
2
The job mridanga-parent-notices (every minute) calls the Edge Function notify-parents, which claims a new 6-digit code (stored only as a hash) and sends the email through Brevo, in the child's app language. Limits: 5 emails per sign-up, 3 a day per address, 60 a day for the whole app.
3
The parent opens Consent for your child (app/src/app/parent-consent.tsx, open without a login), types the code, declares they are the parent or legal guardian and 18 or over, and says yes to the data (a photo is a separate, optional yes). give_parent_consent records it with the privacy-notice version shown.
4
Only now the child appears on the Welcome desk. They come with the parent; the coordinator looks at the parent's ID document and records only its kind (Aadhaar, PAN, …), never its number, then taps Accept.
5
accept_minor_sign_up writes the student (linked to the child's login), the guardian and the consent of method email_code, and deletes the request. Without the parent's yes within 30 days, or without the desk within 180 days, a nightly job erases the whole sign-up (mridanga-minor-signups).

The rule that holds everywhere

Whatever the path (this one, the desk form, the Excel import, the dashboard), a trigger checked at commit refuses a student under 18 on record without a current data consent given through one of their own guardians, and a guardian with a phone (minor_rule_gap, errors minor_needs_consent, minor_needs_guardian; DECISIONS #16, #272). The desk form's equivalent for a parent who signs on paper: the coordinator ticks that the signed form was received (signed_form).

7. Journey: QR check-in, check-out, attendance

1
My QR card (My QR tab) shows a QR code holding MS1: and the student's secret qr_token, not the roll number, so nobody can make another student's code by guessing (DECISIONS #17). The last one loaded is kept on the phone. A student without a phone gets a printed card with the same code (Print QR cards, 0045); a lost card is re-issued with reissue_qr_code and the old one stops working.
2
The coordinator opens Check-in (tab) (staff/mark-attendance.tsx) and scans with the camera (expo-camera; on the web, the browser's reader or zxing-wasm on iPhone Safari). Without a camera they search the name and tap Check in / Check out.
3
scan_qr → toggle_visit: check in if the student has no open visit, else check out, all in one transaction. A second scan within 10 minutes of a check-in answers "already in", so a second phone or a retry does not end the visit. mark_visit does exactly what the button says and locks the student's row while it works.
4
The answer carries the student's name, roll number and time. Any check-in makes the student Active and closes their open follow-up tasks.

The location flag (0024, DECISIONS #70)

A check-in also sends the marking phone's position (foreground only, at most 8 s). The database compares it with the centre's point and radius (set on Centres) and stores only the result and the distance, never the position: inside, outside, refused, no_fix, no_location, no_area. Outside or unknown is saved anyway but flagged for the Guru and counted in the reports.

Closing time, and days without signal

  • In class now lists open visits; at closing time Check out all (check_out_all) closes them.
  • Every hour the job mridanga-close-visits closes any visit still open an hour after its centre closed, at the closing time (21:00 India time for Abids). Each centre has its own time zone (0033).
  • Staff may correct only a visit's times, and each correction is in the change history (0030).
  • NEXT No signal at the door (DECISIONS #593): a scan or tap is kept on the door phone (lib/offline-queue.ts) and sent when the signal is back, the same class day only, with a request id so it is saved once. A scanned code is re-sent only as a check-in, because scan_qr toggles.

The student sees their visits in My attendance; staff see them on the student's page and in Reports (class_report, with a CSV download).

8. Journey: follow-up calls and student status

In a drop-in class nobody notices when a student quietly stops coming. So the database watches the days since the last visit, and gives the student's mentor (a coordinator) a call to make.

1
Every morning at 06:00 India time the job mridanga-status-refresh runs refresh_student_statuses(): no visit for 14 days → Irregular and a call task for the mentor, due in 3 days; 30 days → Inactive. The numbers are rows in settings (the Guru changes them in Settings), not code.
2
The coordinator opens Follow-ups (tab) (staff/(tabs)/follow-up.tsx): students grouped as needs the Guru, call due, call later, and Irregular or Inactive with no call planned.
3
Record a call (staff/call/) has buttons that open the phone's dialler for the student or, for a minor, the parent. Afterwards: the outcome, a reason from the list (studies, work timing, moved, health…), a comment and, for "coming back" or "taking a break", a date.
4
log_call saves the call and applies the outcome: taking a break → Paused until the date; stopped coming → Left; coming back → a new call for the day after the date; not reachable → a retry, and after several failed tries in the same absence the task is escalated to the Guru.
Why only through a call? A trigger refuses setting Paused or Left directly (DECISIONS #4), so nobody is dropped from the class without a reason and a comment. Every status change is kept in status_history, every call in call_logs. Call notes are private: coordinators read them only through get_call_notes, which writes a row in the access log (section 15).

9. Journey: learning: progress, lessons, assessments, level-ups

Levels and the syllabus

There are three levels: Beginner, Intermediate, Advanced (table levels). Each has an ordered list of syllabus_items, which the Guru edits in Lessons (staff/levels/); items are retired, never deleted, so no tick is lost (DECISIONS #44).

Mark progress (ticks)

When a student shows an item in class, a coordinator ticks it in Mark progress (staff/syllabus/): a row in student_progress with the date and an optional remark. The trigger student_progress_guard writes the real ticker's id whatever the app sends, refuses a future date, and freezes the tick except its remark; every tick and untick is copied to the change history (DECISIONS #22). The student sees it in My progress.

Lessons (materials)

Each level or item can have lessons: a YouTube link, a video file link, a PDF or a photo (materials, files in the private bucket material-files). A student sees approved lessons up to their own level. Lesson video plays YouTube in YouTube's own embedded player (never altered, as YouTube's terms require) with speed, A-B loop and, for the team's own videos, mirror and camera-angle zoom. Coordinators can suggest a lesson; the Guru adds or declines it.

Level-ups (promotion)

The app never promotes anyone by itself (DECISIONS #53).

  1. promotion_criteria checks a student against the Guru's settings: the level's syllabus ticked, 8+ visits in 8 weeks, an accepted level-up recording.
  2. A coordinator recommends the student with a reason and asks other coordinators (nominate_for_promotion).
  3. They answer Ready / Almost / Not yet with a comment; at 2 answers it waits for the Guru (Level-up queue).
  4. The Guru decides: Promote (students.level_id + a level_history row), Not yet with a date, or More feedback. A trigger refuses any other change of level.

Screens: staff/assessments/, student/assessments/, staff/promotion/, staff/levels/, staff/materials/, screens/lesson-player.tsx. Tables: see section 16.

How the sound keeps time

In the browser (practice-audio.web.ts): Web Audio. A timer every 25 ms looks 150 ms ahead and schedules each sound on the audio clock, not on the timer. Measured on 3-10-2026: 183 clicks in 136 s, worst error 0.16 ms, none late, even in a background tab.
On the phone (practice-audio.ts, expo-audio): one cycle is mixed into a WAV file and played on loop, so the audio hardware keeps the time. A tempo change writes a new file and seeks to the same beat.

Who sees the practice

The student sees their own week and milestones; staff see each student's week in Practice this week (staff_practice_week(), least practice first, so the mentor knows whom to encourage). The "How did it go?" rating is new data about a child, so the privacy notice names it.

NEXT Without signal, Stop counts the minutes there and then and keeps the entry on the phone; it is sent once the signal is back (DECISIONS #593, #594).

11. Journey: news, notifications, events and polls

News (announcements)

A coordinator or the Guru opens News (tab) → New: title, message, up to 3 photos or PDFs, who it is for (all students, one level, my mentees, staff only, or a group), pin or not, now or at a later time. The app shrinks photos, uploads them to the private bucket announcement-files and saves the row in announcements; triggers check it and record the author. A file opens only for people allowed to read its announcement, through a signed link that expires (DECISIONS #32).

  • Seen by N of M: opening a post writes a read receipt; the views announcement_seen and announcement_audience count them, with the names of those who have not seen it.
  • Private replies: a reply is read only by its writer, the author and the Guru (DECISIONS #29).
  • Groups replace the WhatsApp groups; a group is switched off, never deleted.

How a notification reaches a phone

The inbox (the bell on the home header, Notifications) is filled for everyone, with or without push, so the web version's users see new things when they open the app. The phone registers its Expo push token with register_push_token (at most 5 phones a person). Phones unused for 90 days lose their token NEXT (retention job, 0060).

Events and polls

Events: a programme with date, place and audience; people answer whether they are coming (rsvp_event); staff mark performers and who came; "Add to calendar" makes a calendar file. Polls: one question, people vote through vote_poll; nobody, not even the Guru, can read the votes table directly, and in an anonymous poll the functions never show anyone what a person chose (DECISIONS #61). A daily job at 09:00 sends the day-before and closing-day reminders.

12. Running the class: fund, instruments, roster, reports

Class fund (Class fund, 0026)

  • An income and expense ledger in fund_entries, amounts in whole paise (integers, never decimals), shown as ₹1,25,000.50. Bills go to the private bucket fund-bills.
  • Maker-checker: larger expenses wait for approval, and nobody approves their own entry. Treasurers are coordinators the Guru marks.
  • Append-only: a trigger refuses deletes and edits for every role, the dashboard included. A mistake is a reversal row with a negative amount.
  • The app writes the ledger only through functions (record_fund_entry, decide_fund_entry…), so the rules hold on every path. Students and parents see no money.

Instruments (Instruments, 0023 + 0035)

  • Every seva asset has a code (e.g. KHOL-007) and an unguessable asset_token. Print labels prints an A4 sheet of 18 QR labels from the browser; the label is a web link, so any phone camera opens it, and the app shows it to staff only.
  • Lending and taking back are functions (one open loan per item; no damaged item out); every condition seen is a row in inventory_checks. Count instruments runs a stocktake.

Seva roster and suggestions

Seva roster: the Guru plans duty shifts with their people in one call (save_duty_shift); a job at 18:00 reminds everyone on tomorrow's duty. Suggestions: a coordinator suggests a lesson; it stays hidden from students until the Guru adds it.

13. Parents by email, and Ishtagoshti for everyone

Check-out email to a parent OFF (0043, 0044)

14. Security: roles, row-level security, keys

Three layers, only one of them is the lock

Roles and areas

src/auth/auth-provider.tsx works out the person's area from the login and its profiles row: signedOut, recovery (set a new password), signInCode, pending, guru, coordinator, student, subscriber, or loading. src/app/_layout.tsx opens only that area's screens; the staff/ folder is shared by the Guru and coordinators. When the database refuses a call as not allowed, the app reads the profile again, so a login switched off while the app is open moves to "Account switched off" at once.

Rules every maintainer must know

  • RLS is on for every table; the test net fails if a new table has it off. Policies call their role helpers as (select is_staff()) so Postgres asks once per query, not once per row.
  • Views read as the person asking (security_invoker = true), so RLS still applies under them.
  • Every function is revoked from everyone and granted only to the roles that need it; role checks are NULL-safe, so a switched-off login is refused like a stranger. Someone not signed in (anon) may run exactly one function, sign_up_choices().
  • Nobody gives themselves a role. Only the Guru gives roles; the Guru role itself is set only in the Supabase dashboard.
  • A child's record has no side doors: the login link, QR token and consent fields are frozen for app users; consents are insert-only and checked at commit.

Keys: what is public and what is secret

Public (in every copy of the app): the project's URL and its publishable key. Fine to ship: the key only opens the front door; RLS decides everything after it.
Secret (never in the app, the repo or a chat): the service_role key, which skips every rule. Only the two Edge Functions use it, inside Supabase. The app refuses to start if it finds it in .env (src/lib/supabase.ts), and the publish scripts scan the bundle for it.

Staff sign-in codes NEXT (0061, DECISIONS #580-#589)

A Guru or coordinator can add a 6-digit code from an authenticator app (Supabase Auth's TOTP). Once every staff member has one, the Guru may switch staff_mfa_required on: then parents' details, consents, call notes and the logs are read only by a session that gave the code. The switch refuses to lock out the only Guru. A lost phone: the Guru resets the code in Sign-in codes.

Also: the web version sends strict security headers (a Content-Security-Policy naming only its own Supabase address, HSTS, nosniff), written by the export script from app/public/_headers. Every sign-out clears the QR card, notifications, cached photos and picked files from the device (src/lib/device-traces.ts).

The smoke test: a whole database on your laptop

supabase/tests/smoke-test.mjs starts PGlite (PostgreSQL compiled to WebAssembly, in memory: no server, no Supabase account), imitates Supabase's auth schema, roles and Storage, runs every migration and seed.sql, then tries what each kind of person might do and checks the database allows or refuses it, with the exact error code. It ends with All 2224/2224 checks passed, and fails if the count differs from EXPECTED_CHECKS, so a skipped block cannot pass unseen.

After the per-migration sections comes the test net: it walks the whole schema: every table has RLS; every function the app may run is on an allow-list (SIGNED_IN_MAY_RUN); a student-isolation loop over every column that names a student; write sweeps per role; triggers and jobs.

The LIVE replay (live-replay.mjs): builds a database at LIVE's old state with rows of every kind, applies the later migrations in order, runs each file twice (the second run must change nothing), and compares the result with a fresh build. A new migration fails it until the go-live checklist lists it.
What PGlite cannot prove: real pg_cron timing, pg_net calls, Storage size limits, two sessions at once, Supabase's own MFA. These are listed at the top of the smoke test and checked by hand on TEST.

CI: GitHub Actions (.github/workflows/ci.yml)

On every pull request and every push to main, three jobs run with Node 24: App (npm ci, lint, typed routes, tsc, npm test), Database (the whole supabase/tests npm test) and Website. They need no secrets and only read the code. Actions are pinned by commit SHA; Dependabot proposes updates weekly (npm) and monthly (actions). A red run: open the failed step, read the first FAIL line, fix on the branch, push again.

CI is not everything. It does not run the app on a phone, deploy, publish or touch TEST/LIVE. Screens have no automatic tests yet: check a changed screen in a browser as each role (phone width 375 px and laptop 1280 px) on TEST, and describe how in the pull request. "It builds" is not "it runs".

Adding a test

  • A pure helper in app/src/ → a node --test file in app/tests/ (a native package gets a stub in tests/stubs/).
  • A migration → a new section in the smoke test: the roles that must be refused (refusesWith(name, 'exact error', fn)) and the role it is for; then set EXPECTED_CHECKS to the new total.
  • A new function the app calls → add it to SIGNED_IN_MAY_RUN. A new table → RLS on; its student_id / profile_id columns are checked by the isolation loop on their own.

20. Release and operations

An APK has two layers

Build (a new APK) = the whole app, native code included. Made on Expo's servers (EAS Build), free queue up to an hour or more, 15 a month. Needed when anything native changes: a package with native code, an Expo SDK upgrade, app.json, eas.json, the icon. Everyone installs it once.
Update (OTA, "over the air") = only our JavaScript: screens, words, colours, logic. Published in minutes; the app downloads it at start and offers Restart now. Reaches only APKs with the same fingerprint.

The fingerprint is a hash Expo computes from everything native. The class's production APK (build 90c6d1cd, 16-10-2026) has fingerprint 23dc7e4a. Check yours with npx expo-updates runtimeversion:resolve --platform android in app/: unchanged → an update is enough. That is why native changes are grouped for one planned APK, and why face scan, with its native libraries, waits on its own branch.

Database first, then the app (DECISIONS #121)

Why this order: an app update reaches phones within minutes, so if it calls something LIVE's database does not have yet, the class's app breaks. And migrations stay additive for one release: never drop or rename what the app in use calls, so a bad update can always be rolled back (npx eas-cli update:rollback) without touching the database.

You will see this in the git history: small branches, merge commits, and a decision entry and documentation with each change.

A change is not finished until its documentation is (docs/README.md). Behaviour changed → DATABASE.md or ARCHITECTURE.md; a new rule or trade-off → a DECISIONS entry; a new screen → SCREENS.md; a new term → GLOSSARY.md; something users see → a line in app/src/content/whats-new.json before the next production update.

Where the screen list came from

Before any code, on 28-09-2026, every screen the app might need was listed for the team (about 80, each with a code like A1 = login, C5 = mark attendance, G4 = syllabus editor) with Approve / Change / Drop. The team's answers shaped the app: three roles, no batches, three levels, email login, English first with Telugu and Hindi, parental consent, and Phase 1 must cost nothing. The codes live on in the docs and code comments.

22. How to contribute safely

The three rules that protect the children's data
  1. Never LIVE. Never run anything against the LIVE project (qeozvv…). The main checkout's app/.env on the maintainer's PC points at LIVE: work in your own clone or a worktree whose settings point at TEST (fhuqyk…). A deploy command is never a test: on a PC where the Supabase CLI is logged in, it really deploys.
  2. Never real data. Only the fictional seed students in code, tests, seeds and screenshots.
  3. Never secrets. No .env file, service_role key, password or keystore in git or a chat. .gitignore refuses the usual ones.

Your first change, step by step

1
Agree first. Open or pick an issue on GitHub (Praviadari/mridanga-seva); for anything larger than a small fix, agree the approach before coding.
2
Set up. Node 24 (.nvmrc). Clone, cd app, npm ci; copy .env.example to .env.development with the TEST URL and publishable key; npx expo start and press w for the web version. In supabase/tests: npm ci, npm test.
3
Branch from main (e.g. fix/attendance-checkout). Never commit to main directly.
4
Change, following the house rules: words only in en.json + te.json + hi.json (never in a screen); screens call data/, never Supabase directly; a database change is a new migration with RLS, comments, revoked-then-granted functions and smoke checks; Expo packages with npx expo install; a header comment on every file; "prefer boring code".
5
Check: the commands of section 19, all green; the screen tried on TEST as each role it concerns, at phone and laptop width.
6
Native or not? If you added a package or touched app.json / eas.json, compare the fingerprint. A change of fingerprint means a new APK: say so in the pull request, it is merged only when a build is planned.
7
Document: DECISIONS entry, DATABASE / ARCHITECTURE / SCREENS lines, What's new if users see it.
8
Pull request: one change, a clear description, screenshots for a screen, how you checked it. CI must be green. Merging, pushing to main, running a LIVE migration and publishing stay with Praveen.

Common traps (from real mistakes)

TrapWhat to do
A function raises a sentence instead of a codeRaise a short snake_case code; explain in detail; translate it in the app
New function callable by everyoneSupabase grants new functions to PUBLIC: revoke from public, anon, authenticated, grant only what is needed
Editing a migration that already ranNever. Add the next number. Two branches may both use a placeholder number; the lead renumbers at merge
Calling a new database function from an update before LIVE has itDatabase first (section 20); or make the app fall back when the function is missing
A route path typo passes tsc on a fresh cloneRun node scripts/typed-routes.mjs before npx tsc --noEmit
Uploads to Expo fail half-wayThe office network: use a phone hotspot. Never switch certificate checks off
"It works in development"Test the real APK or the exported web version too; never hide an error from the user

24. Glossary

APKThe Android app file people install from a link.
AreaThe set of screens a person may open: signed out, pending, student, staff (Guru and coordinator), subscriber…
Audit log / Change historyThe database's record of who changed what, and when.
Access logThe record of who read a child's private details (parents, consents, call notes).
BolA spoken syllable for a drum stroke (dha, ta, ghe…); a taal is a cycle of bols.
BucketA folder in Supabase Storage with its own rules (ours are private).
CIContinuous integration: GitHub runs the checks on every pull request and push to main.
ConsentA row in consents: what was agreed (data, photo, weekly email), by whom, how, when, which notice version.
DPDPIndia's Digital Personal Data Protection Act 2023 and its Rules 2025.
Edge FunctionA small server program on Supabase: notify-announcements, notify-parents.
EAS Build / UpdateExpo's cloud services that build the APK and send JavaScript updates.
Erasure / tombstoneDeleting a person's data for good; the tombstone keeps only the roll number, date, reason and reference as proof.
Expo / React NativeTools to write one TypeScript app for Android, iPhone and the web.
Expo RouterEvery file in app/src/app/ is a screen and a web address.
FingerprintA hash of the app's native parts; an update reaches only APKs with the same one.
FacilitatorThe Guru, as the English screens call the role guru.
Guard / triggerA check the database runs when a row is saved; it can refuse the save.
i18n"Internationalisation": every word in en.json, te.json, hi.json, fetched with t('key').
IshtagoshtiSloka (verse) study; also open free to the public.
LIVE / TESTThe class's real Supabase project / the one with made-up data for building and testing.
MentorThe coordinator who follows a student up with calls.
MigrationA numbered SQL file that changes the database; never edited once run.
OTA updateNew JavaScript sent "over the air" to installed apps, without a new APK.
PendingA login waiting for the desk; it reads only its own profile.
pg_cronThe timetable inside PostgreSQL that runs our 17 jobs.
PGlitePostgreSQL that runs in memory inside Node; our tests use it.
Publishable / service_role keyThe public key every app holds / the secret key that skips every rule (Edge Functions only).
Roll numberMS-2026-0042: given by the database, frozen, never reused.
RLS (row-level security)Per-table rules in PostgreSQL deciding which rows each person may read or change.
Security definer / invokerA function that runs with its owner's rights (and checks the caller itself) / with the caller's rights.
Seedsupabase/seed.sql: the fictional students of the TEST project.
Smoke test / test netThe 2,224 database checks run on PGlite; the net is the part that sweeps the whole schema.
SupabaseThe hosted service around our PostgreSQL database: login, storage, functions, jobs.
TaalA rhythmic cycle of beats; the practice player loops it.
VisitOne check-in and its check-out: a row in visits.
WorktreeA second working folder of the same git repository, on its own branch.
